# BolPrep

BolPrep is a beginner-built portfolio project for learning how to make a Hindi and Hinglish voice study tutor. Its first topic is Indian Polity, starting with Fundamental Rights.


## Current status

Tutor NDJSON responses are limited to 2 MiB of received bytes and 262,144 UTF-16 units per event line. The client rejects invalid JSON, unsupported/malformed event types, invalid completed payload containers, empty final answers, and nonblank events after completion. Incomplete streams remain failures. It cancels unread data and releases the reader; existing request recovery stops progressive speech and restores controls. These bounds cover accumulated processing, not transport buffers or one delivered chunk, and large legitimate replies can be rejected. Stream fragmentation, rejection/recovery, and server compatibility remain unverified at runtime.

Recorded transcription returns up to 6,000 Unicode code points for review, so a transcript beyond the question limit can be edited instead of discarded. The browser keeps the returned words and warns when they exceed the current composer limit (including the shorter quiz-answer limit); it never submits a recorded transcript automatically. Submission still requires shortening it to the existing limit. Longer provider transcripts are rejected with a request to record a shorter clip, and the previous draft remains available. Browser input limits count UTF-16 units, which can differ from server code-point counts for some characters. Long-transcript review and quiz behavior remain unverified at runtime.

Record watches for permanent microphone track loss and rejects missing/already-ended audio tracks at startup. Device loss discards the partial recording, records `capture-ended`, releases tracks, and asks the learner to reconnect or type. A recorder that stops before the track event also checks track state before uploading. Normal recording Stop and the 20-second limit keep their transcription path; lifecycle cancellation discards the clip. Temporary track mute is not classified as permanent loss. Device removal, permission revocation, event order, duplicate failure suppression, and ordinary Stop remain unverified in a browser.

Hiding or leaving the page cancels all speech input paths: browser recognition, live transcription, recorded capture (including pending microphone access), and recorded transcription requests. Unconfirmed browser/live words are discarded using the existing draft restoration rules; confirmed browser words remain for review. Recorded clips are discarded and their tracks receive immediate stop commands, without waiting for recorder completion. Returning to the page requires an explicit new microphone action. This does not stop an already-submitted tutor response or undo provider processing already started. Browser lifecycle events, permission races, and device microphone release remain unverified at runtime.

**Implemented:** Step 0's fixed-answer Python exercise and a local browser tutor prototype. It accepts typed questions, retrieves a matching note from a checked forty-eight-note corpus, links the Constitution source, can use a configured OpenAI model through a small Python server, and speaks answers with the browser's built-in speech synthesis, with a selectable, previewable installed voice when the browser exposes one for the chosen language, or with optional streamed OpenAI speech using one of 13 selectable provider voices when enabled; speech language and per-language voice preferences are saved in browser storage. Where supported, browser speech recognition can fill the question box; an unchecked, session-only option can automatically submit a final transcript when listening ends naturally. The option is off by default; Stop keeps the final transcript for review, and interim-only text is never submitted. Late events from a canceled listening session are ignored, editing the question box stops active recognition so it cannot overwrite the edit, a later interim result or error does not replace a final transcript or its ready status, and an attempt that ends without a final transcript or is stopped with Speak, the tutor Stop control, Escape, or a speech-language change restores the text present before listening, while stopping after a final transcript keeps it for review. Submitting while only interim words are available waits for a final transcript instead of sending unconfirmed text. A recognition error also releases the Speak control immediately and counts a failed attempt once. When configured, a separate Record control can capture up to 20 seconds and send it for server-side transcription; the same control can cancel capture while microphone access is pending or cancel transcription; the speech language is captured when recording starts and stays fixed for that clip, the editable transcript is shown before submission, editing the question box cancels recording or pending transcription so it cannot replace typed text, and BolPrep does not save the audio. Submitting a question cancels an unfinished recording or transcription so a late transcript cannot overwrite the composer. The quiz uses checked questions and deterministic rubric scoring, saves progress locally, and exposes quiz and weak-topic functions to model requests only when the user message matches quiz or revision intent; ordinary explanation turns omit tools. Without an API key, the tutor remains usable in a clearly labeled offline mode, including English, Devanagari Hindi, and Roman Hinglish notes. Quiz and revision commands require recognizable request phrases: English or Roman Hinglish quiz requests like `quiz me`, `start a test`, `quiz karwao`, and `mera viva lo`; Devanagari quiz recognition requires an action after the word for quiz, such as `lo` or `karao`. English and Roman Hinglish revision requests include `help me revise fundamental rights`, `revise Article 14`, `revision karao`, `weak topics`, `where am I weak`, `kamzor topics batao`, `kamzori dikhao`, and `dohrao fundamental rights`. Questions about a revision petition or procedure stay on the explanation path; isolated mentions of `test`, `viva`, `revision`, `weak`, `kamzor`, or `dohra` do not trigger quiz or revision tools.

With browser speech selected, ordinary model replies queue complete sentences as the text streams; long sentences are split at word or character boundaries. Offline answers and quiz or revision turns wait for the full answer before speaking. Optional provider TTS now queues complete sentences from ordinary streamed model replies and plays each segment serially; offline answers and tool turns still wait for the full answer.

Submitting a typed follow-up stops any current browser or streamed speech playback as the new request starts, so queued audio does not continue while the tutor is thinking. Canceling quiz preparation re-enables the quiz button, while a late canceled request cannot re-enable it during a newer quiz request. Stopping between quiz questions keeps the next question available; canceling or failing to start a replacement quiz restores it. Stopping quiz scoring or receiving a scoring error restores the submitted answer only when the student has not started a new draft in the input box. Retrying the same answer keeps its retry key; a revised answer gets a new key, so an earlier saved score is reported as a conflict instead of being shown for the revision, and the status directs the learner to start a new quiz. A successful replacement quiz clears the previous answer draft, and completing a quiz restores the question length limit. Browser and device behavior should still be checked with the turn-taking run sheet.

**Experimental:** when an API key is configured, the tutor can stream OpenAI-generated PCM speech from the server to the browser and choose among 13 built-in voices. The [official TTS guide](https://developers.openai.com/api/docs/guides/text-to-speech) documents streaming and Hindi support, and notes that built-in voices are optimized for English. With browser speech selected, ordinary model replies queue complete sentences as the text streams. Quiz or revision turns wait for the full answer before speaking. For ordinary streamed model replies, optional provider TTS starts with the first complete sentence and combines waiting sentences into segments of up to 1,000 Unicode code points. Each segment uses a separate billable speech request and counts toward the local speech quota; segments play serially and may have audible gaps. Hindi is listed as supported, but built-in TTS voices are optimized for English, so Hindi/Hinglish pronunciation has not been evaluated. Browser speech remains available as the default and fallback. A configured API key also enables optional recorded-file transcription; recordings are sent only after the user stops, and no audio is saved by BolPrep. This is a bounded upload, not live STT. In model mode, [Responses API text deltas](https://developers.openai.com/api/docs/guides/streaming-responses) now render incrementally in the conversation; offline answers still arrive as one completed response and are spoken after completion. The client closes its local response stream when stopped, but provider-side cancellation is not verified. **Not implemented yet:** speech quality benchmarks or measured end-to-end voice latency. Continuous conversation mode is experimental and awaits real-device validation. The browser displays speech-start delay and playback duration for each playback request as diagnostic timings only; browser chunked answers are measured as one request. Progressive provider speech is measured per segment under sample_type tutor-segment; its start delay begins when that segment is requested, excluding time spent waiting in the sentence queue or for model text. These values are not full-answer latency. Quiz scoring matches rubric phrases and does not interpret meaning. The Responses API tool loop has mocked tests but has not been exercised against a live model; model mode needs the optional SDK and an API key. Browser speech recognition and installed Hindi/English speech voices vary by browser and device; if no voice for the selected language is installed, the browser may use a different default voice. The UI reports per-page model-mode request-to-first-text and request-to-completion p50/p95 by configured model and language, failure counts, and cancellations (including late completions from stopped turns), plus browser STT time-to-first-final p50/p95 and failed/empty attempt counts by language (including recognition start failures), recorded-file STT upload-to-result p50/p95 and failure counts by language, plus TTS p50/p95 start and playback timings by language, voice, and sample type with failure counts for each group; exported `start_event` identifies whether start timing comes from browser synthesis or a scheduled streamed PCM buffer, not acoustic latency. With opted-in automatic browser voice turns, diagnostics also report recognition-end to first TTS start-event p50/p95 grouped by input/output language and start event; this software interval is not acoustic latency or a measure from the end of learner speech. For progressive browser speech, start delay includes model generation until the first complete sentence can be spoken. These speech diagnostics reset on reload, retain at most 500 successful timing samples and 500 failure records per path in page memory, and do not store speech text or audio or measure pronunciation quality. Recorded-file timing starts when the completed clip begins upload and ends when its transcript reaches the browser; it excludes capture time and is not speech-end latency. When progressive browser speech fails, its error stays visible while the text answer finishes; the answer stays readable on screen. The starter corpus has source-linked notes for Articles 12 through 51 and Article 51A, including the note on Article 31 omission; Articles 43A and 43B are included. The Article 19 note lists its six currently lettered freedoms, identifies omitted sub-clause (f), and distinguishes restriction clauses (2) through (6). Unsupported questions should receive an insufficient-evidence response.

## Run the text tutor

On Windows, start the complete local setup with one command from the project folder. The launcher reuses a working Python 3.11+ virtual environment or finds Python through `python` or the Windows `py` launcher:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\run-local.ps1
```

After setup, check the offline app end to end with:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\check-local.ps1
```

The smoke check starts a temporary local server in offline mode without sending requests to a model provider, checks the health endpoint and tutor page, asks a Hinglish Article 14 question to confirm a source comes back, then starts and scores a quiz and verifies an idempotent retry appears once in saved progress. The progress uses a temporary SQLite file that the script removes when finished, so it does not touch normal learner progress. Port 8000 must be available.

The launcher reuses `.venv` when its Python interpreter runs and is version 3.11 or later. If `.venv` is missing, broken, or too old, it creates a fresh environment using the selected system Python; rebuilding clears only the project `.venv` directory. A linked `.venv` is left for manual repair rather than cleared. It installs `requirements.txt`, copies `.env.example` to `.env` only when `.env` does not already exist, and starts the server. Open <http://127.0.0.1:8000>; press Ctrl+C in PowerShell to stop. Add an API key to `.env` before starting if you want model answers. Offline mode works without a key.

For manual setup, create and activate the environment, then install dependencies:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Put your API key in `.env` to enable model answers. Keep that file private; it is excluded from Git. The default model can be changed with `OPENAI_MODEL` in `.env`. Start the local server, then open its address in a browser:

```powershell
.\.venv\Scripts\python.exe server.py
```

Open <http://127.0.0.1:8000>. The server binds to localhost and keeps the model key on the server. Its `/health` check reports setup mode and corpus size without creating a browser progress session; static JS and CSS requests also avoid session storage. Browser microphone permission is requested only after you click **Speak**, **Record**, or **Live mic**. While listening, the same button changes to **Stop** so you can end capture without sending the transcript; you can review the text before submitting it. Press Ctrl+C to stop the web server.

Without an API key, the tutor returns matching local study-note summaries and source links; it labels these as notes rather than generated explanations. Questions outside the forty-eight-note corpus receive an insufficient-evidence response. The smaller Step 0 example can still be run with:

```powershell
python step0.py
```

## Continue repo work in the background

With the Codex CLI installed and signed in, start the bounded roadmap loop:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\start-work-loop.ps1
```

By default it runs for up to eight hours and up to 24 focused tasks, spaced about 20 minutes apart. Waits use absolute UTC due times, so a pause does not add the full wait again after resumption; the original deadline still applies. Each task has a 60-minute timeout by default; set `-TaskTimeoutMinutes` when starting the loop to change it. Each run uses the Codex CLI's workspace-write auto-approval mode, checks the repository roadmap, verifies its change locally, and creates a focused commit and pushes it to `origin` after its checks pass. It does not publish releases or deploy. Failed CLI invocations are retried on the next loop pass with a capped delay. The runner checks for stop requests at least every 30 seconds while waiting and stops when a task reports that it needs your input. Use `powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\stop-work-loop.ps1` to request a graceful stop after the current task. The process-scoped execution-policy option does not change the machine's PowerShell policy. Status and per-run logs go under `.codex\overnight\`, which Git ignores. The task boundaries are in [AUTONOMOUS_WORK.md](AUTONOMOUS_WORK.md).

## Intended voice tutor

The planned end-to-end experience is a student asking in Hindi, English, or Hinglish for a short explanation, then asking the tutor to quiz them. The target system will speak its answer, ground explanations in a small checked corpus, score spoken answers against a rubric, and save progress.

A central voice-engineering challenge is interruption handling. When a student speaks while audio is playing, the tutor should stop playback, cancel the old generation, preserve conversation context, and ignore late results from the interrupted turn. The current client keeps an interrupted pending question with an explicit interruption note for the next turn and the server quietly handles the resulting disconnected socket; provider-side generation cancellation remains incomplete. The project also aims to compare speech configurations on the same examples and report measured quality and latency, including failure cases.

## Target architecture

```text
Browser microphone
  -> speech detection and STT
  -> turn controller
  -> LLM with retrieved study material and validated tools
  -> streaming TTS
  -> browser playback

Backend -> session and progress storage, trace events
Evaluation runner -> fixed examples, comparisons, and reports
```

The current prototype uses a Python standard-library HTTP server and plain HTML, CSS, and JavaScript. OpenAI Responses API is the optional text model; speech recognition and speech synthesis use browser-provided features. This keeps setup small while making browser and device support a known limitation. SQLite stores local quiz progress. Optional streamed OpenAI TTS, recorded-file STT, and live WebRTC STT are implemented as experimental provider paths; compare language support, streaming behavior, quality, and cost before relying on them.

## Live microphone transcription (experimental)

With `OPENAI_API_KEY` configured and dependencies installed from `requirements.txt`, **Live mic** opens a WebRTC transcription connection. Allow microphone access, speak, and tap **Done**. Partial text appears while speaking; only the completed transcript can be submitted. Review it before asking or scoring a quiz answer. Capture finishes at the selected 20- or 60-second live limit if you do not tap Done.

The server keeps the project key private and returns a short-lived connection credential that expires after 60 seconds. Audio travels directly from the browser to OpenAI; BolPrep does not save audio or connection credentials. API usage may be billed. **Stop**, **Escape**, language changes, typing, or leaving the page close capture; partial words are discarded on cancellation, while typing preserves the edit. Connection and final-transcript waits have deadlines. A failure restores your previous draft; use **Record**, **Speak**, or typing to retry.

This follows the official [Realtime transcription](https://developers.openai.com/api/docs/guides/realtime-transcription) and [WebRTC connection](https://developers.openai.com/api/docs/guides/voice-webrtc?api=realtime) guides with `gpt-live-transcribe`, expected Hindi/English languages, and client-controlled audio commits. Optional browser energy-based pause detection and opt-in continuous conversation are implemented; real-device interruption behavior remains unverified. The 250 ms delay before committing is a best-effort media drain, not a guarantee across network conditions. Live transcription has not been exercised with a real microphone/provider. Diagnostics schema 12 exports live STT software-event timings and outcomes, including continuous mode and connection reuse.

Enable **Finish Live mic after a quiet pause** before starting capture to try automatic completion. Choose 3 seconds (default), 5 seconds, or 8 seconds under **Quiet pause before finishing**; the setting applies to the next connection and is disabled during capture. It is off by default and never submits the transcript automatically. The browser uses a [Web Audio analyser](https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode) without speaker output: an RMS level of at least 0.015 for 250 ms establishes activity, followed by a level below 0.008 for the selected quiet-pause duration to finish. These are heuristic settings, not measured quality results. Noise or a quiet voice can defeat detection; Done and the selected live capture limit remain available. Delayed sampling resets pause evidence, and unavailable or suspended audio analysis falls back to Done. Audio samples are not persisted or exported by this detector.

**Live STT diagnostics:** Copy or download Speech diagnostics for up to 500 terminal attempts on the current page. `live_stt_attempts` records language, configured model, UTC start time, completion/failure/cancellation, finish reason, and pause-detection use or fallback. It includes connection readiness time (initially starting before microphone permission; on reuse, starting before buffer clearing), listening-to-first-partial time, listening duration, commit-to-final time, and total duration. Missing events produce null timings. `live_stt` groups by language, model, requested pause detection, selected quiet-pause duration, whether analysis ever ran, conversation mode, and connection reuse; it reports p50/p95 and sample counts for completed attempts, plus separate failure/cancellation counts and reason breakdowns. Manual Done, quiet-pause, and capture-limit endings are distinguished. These intervals do not measure acoustic speech end, transcript accuracy, or pronunciation. No learner text, audio, session cookie, or connection credential is exported; reload clears the records.

### Continuous conversation (experimental)

Enable **Conversation mode** before pressing **Live mic** to skip transcript review and keep the microphone session open for follow-ups. This option is off by default and applies only to that connection. It requires working local pause detection. After sustained sound, a quiet pause of the selected duration commits the turn, and a completed transcript is automatically sent to the tutor or current quiz answer. The client clears the provider input buffer and waits for its acknowledgment before listening again; completed item IDs prevent late events from old turns replacing the new transcript.

When speech is detected during an answer, the client stops playing/queued tutor audio, aborts its old response stream, preserves interrupted context, and keeps the microphone connection. Provider-side generation cancellation remains unverified. **Done** can finish a turn; **Stop**, **Escape**, typing, language changes, hiding the page, or leaving it end capture. The session ends after five minutes, sixty seconds without detected activity, or a connection/detection failure. Each spoken segment has the selected 20- or 60-second limit. The mic is muted while finalization and buffer clearing are pending, so speech during that interval can be lost. Long transcripts pause the mode for editing. Quiz answers can submit automatically. During an active quiz, say **next question**, **agla sawal**, or **अगला सवाल** after feedback to hear the next question; the button also works. Only explicit whole-transcript commands are recognized, with punctuation and whitespace normalized. A next-question command cannot skip an unanswered question and is never scored as an answer. Other speech between quiz questions pauses capture for review.

Use headphones first: speaker echo or background noise can trigger a false interruption or transcript. The energy detector has not been validated with real Hindi/Hinglish audio, devices, natural pauses, or echo. If analysis is unavailable/suspended, conversation mode closes and suggests restarting with the mode off for manual Done. A new connection is required after the session ends; there is no automatic reconnection or background recording.

## Saved quiz progress

Quiz scores are stored in a local SQLite database at `.codex/bolprep.sqlite3`, scoped to a random, HttpOnly browser cookie. Set `BOLPREP_DATABASE_PATH` in the server environment to use a different database file; the local smoke check uses this option for an isolated temporary database. Progress survives a server restart in the same browser. The app saves scores and rubric feedback, not the learner's raw answer text. A per-answer idempotency key makes network retries safe without retaining the answer or its hash. The **Saved progress** panel shows recent weak question areas; **Clear saved progress** deletes records for that browser cookie. This is a local prototype bound to `127.0.0.1`, not a multi-user hosted service with account authentication. Keep the cookie private on shared computers; deleting site cookies creates a new, separate progress history.

## Optional local demo sign-in

Set `BOLPREP_ACCESS_PASSWORD` in your ignored `.env` file to a private, separate passphrase of 16-256 characters, then restart the server. Leave it empty for the existing open localhost setup. Do not use a model API key as the demo password. With the gate enabled, visiting the tutor opens a sign-in page; protected tutor, speech, transcription, quiz, and progress APIs require the access cookie. `/health`, scripts, styles, and the sign-in page are public.

Passwords are checked against an in-memory salted PBKDF2 digest using a constant-time comparison. Successful login issues a random cookie with an eight-hour lifetime; the server retains token hashes in a bounded store of 128 sessions. Relogin rotates the current token, and capacity pressure expires the oldest session. **Sign out** revokes that session and stops local voice/response activity. An expired/revoked API session also stops local activity and redirects to sign-in. Restarting the server invalidates all access sessions. Login/logout and protected writes require the local browser Origin.

The access cookie uses [HttpOnly and SameSite=Strict](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie). Cookies use localhost HTTP here; hosted HTTPS and Secure-cookie configuration have not been implemented. ## Local request limits

The server applies rolling 60-second quotas shared by all local browsers. Admitted attempts count even when validation/provider work fails or an idempotent write is retried. A throttled request returns [HTTP 429](https://www.rfc-editor.org/rfc/rfc6585.html#section-4), a `Retry-After` header, and `retry_after_seconds` in JSON. Wait for that interval and retry manually; the browser does not automatically repeat paid requests.

| Requests sharing a quota | Attempts per 60 seconds |
| --- | ---: |
| `/api/answer`, `/api/agent/turn` | 30 combined |
| `/api/speech` | 60 |
| `/api/transcribe` | 10 |
| `/api/transcription/session` | 6 |
| `/api/quiz/start`, `/api/quiz/score` | 60 combined |
| `GET /api/progress` | 60 |
| `DELETE /api/progress` | 6 |
| `/api/login` | 6 |
| `/api/logout` | 30 |

The limiter is thread-safe, uses monotonic time, and retains only bounded timestamp queues in server memory. Throttled attempts do not extend the retry interval, create a browser session, read an upload, or call a provider. The server closes their HTTP connection because the request body remains unread. Restarting the server resets quotas; changing cookies does not. Static files and `/health` remain available.

These are local development defaults, not a billing cap or a hosted-service abuse defense. Direct WebRTC media traffic and token reuse happen at the provider, outside these HTTP quotas. Hosted authentication, per-account budgets, proxy controls, and deployment hardening remain pending.

Tutor answers, streamed speech, recorded transcription, and live-session creation also share **four simultaneous server request slots**. Busy requests return 429 with `code: "server-busy"` and a two-second retry suggestion; quota rejection uses `code: "rate-limited"`. The server does not queue or automatically retry them. The rolling quota counts busy attempts too. Slots cover body processing through response completion and are released when the handler exits, including validation failures and disconnects. Quiz writes, progress, health, and static files do not use these slots. Live mic distinguishes busy and rate-limit failures in diagnostics.

Socket reads/writes have a 30-second timeout, preventing an idle upload or blocked response write from holding a slot indefinitely. This is an I/O wait timeout, not an overall generation deadline; provider requests retain their existing SDK timeouts. Direct WebRTC media sessions are outside the four-slot gate. Concurrent saturation, timeout recovery, and real provider cleanup remain unverified.

## Progressive provider speech
